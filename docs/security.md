# CREW Security and Privacy Design

This document describes the controls implemented so far and the plan for the rest. It does not claim any certification; SOC 2 / ISO 27001 readiness and regulatory validation (GDPR, UK GDPR, DPDP Act, CCPA/CPRA) require independent assessment, scheduled for Phase 10.

## Implemented in Phase 1

| Area | Control | Where |
|---|---|---|
| Tenant isolation | PostgreSQL Row-Level Security with `FORCE ROW LEVEL SECURITY` on every tenant table; the API's login role (`crew_api`) has no privileges and must `SET LOCAL ROLE crew_app` (RLS enforced) or `crew_platform` (auth bootstrap and console only) inside each transaction, so a forgotten wrapper fails closed | `packages/db/migrations/0001_foundation.sql`, `apps/api/src/platform/database` |
| Cross-tenant references | Composite foreign keys `(tenant_id, id)` make it impossible to point a record at another tenant's row | migration |
| Column-level protection | The tenant role cannot select `password_hash` or `mfa_secret_enc` | migration grants |
| Authentication | argon2id (OWASP parameters), 12+ character passwords with complexity, lockout after 5 failures for 15 minutes, constant-time behaviour for unknown accounts | `platform/auth` |
| MFA | TOTP (RFC 6238); secrets encrypted with AES-256-GCM; tenants can require MFA for everyone; sensitive permissions (roles, billing, payroll, integrations, AI configuration) require an MFA session | `platform/auth`, `permissions.ts` |
| Sessions | 15-minute JWT access tokens bound to a server-side session (checked every request, so revocation is immediate); 30-day refresh tokens stored as SHA-256 hashes, rotated on every use, with reuse detection that revokes the whole session family | `auth.service.ts` |
| Authorisation | RBAC roles with ABAC scopes (own / team / department / entity / tenant), assignment constraints, MFA conditions; list queries filter in SQL; out-of-scope records return 404 so existence does not leak; owner role cannot be granted by non-owners; last owner cannot be removed | `platform/authz` |
| Audit | Append-only (trigger + no UPDATE/DELETE grant) and SHA-256 hash-chained per tenant; written in the same transaction as the change; secrets redacted; verification endpoint detects tampering | migration, `platform/audit` |
| Platform staff | Separate table, signing key, sessions and login; MFA mandatory; no tenant data access without a customer-approved, time-boxed support grant, which is audited in the customer's own trail | `modules/platform-admin` |
| API hygiene | Input validation on every route (zod), uniform error envelope without stack traces, request ids, helmet security headers, CORS allow-list, rate limiting per client address, shared across API servers through Redis when `REDIS_URL` is set and falling back to per-server counters if Redis is unreachable (stricter on auth routes; the Web Portal forwards the visitor's address taken from the right-most `X-Forwarded-For` entry, so the proxy in front of it must set that header), Idempotency-Key support | `platform/http` |
| Attendance | Raw punches append-only (trigger + insert-only grant) and deduplicated; derived days rebuilt, never hand-edited; corrections add punches through approval; payroll locks freeze days. Devices accepted only by registered serial and optional IP allow-list, with request size limits; kiosk tokens stored hashed and kept in the URL fragment; QR codes HMAC-signed, 30-second windows, one punch per person per code; no biometric templates stored | `modules/attendance`, `0003_attendance.sql` |
| Recruitment | Public career site resolves the workspace from its address and then runs inside that workspace's RLS context, returning public posting fields only; applications need consent to a versioned privacy notice, are rate limited per visitor, size limited, CV content-checked (PDF, .docx), and get the same response whether or not the person already applied; manual candidates need a recorded lawful basis; application history append-only with no free text; scorecards hidden from other interviewers until they submit; offer approval needs an MFA session; CV links HMAC-signed per file kind, 5 minutes, audited; erasure on request and automatic retention | `modules/recruitment`, `0004_recruitment.sql` |
| Payroll | Exact integer-paise arithmetic; statutory values saved per entity by a person, never assumed; preparer cannot approve; approval needs a two-step-verified session; finalised runs frozen by database trigger; salary amounts kept out of the audit trail; bank account numbers decrypted only inside the audited bank-file export; CSV exports protected against formula injection; receipts checked by content and served through 5-minute links signed for receipts | `modules/payroll`, migration 0005 |
| Talent | Survey answers stored without any person link (no column, trigger refuses one), invitations carry no time, results and breakdowns withheld below the anonymity threshold, answering not audited; manager drafts private to their author; peer feedback shown to the employee without names and only from three answers; final-rating changes need a reason and are kept; released reviews, submitted feedback and completed learning frozen by database trigger | `modules/talent`, migration 0006 |
| Helpdesk and announcements | Cases visible only to the person, their handlers and HR in scope, never to managers; confidential categories limited to named handlers in the query itself, every handler view audited; case text never written to the audit trail; internal notes hidden from the employee; messages and history insert-only; closed cases, published announcements and acknowledgements frozen by trigger | `modules/helpdesk`, migration 0007 |
| Mobile app | Tokens in Keychain/Keystore via `expo-secure-store` (browser preview labelled); devices bound to one membership and to the sign-in that registered them, remote sign-out revokes that sign-in and push token; push content generic (ids only); offline punches idempotent per device and sequence, refused beyond 72 h or in the future, clock changes and mock locations flagged for review; payslip screen blocks screenshots; no certificate pinning or root detection yet | `apps/mobile`, `modules/mobile`, migration 0007 |
| AI and automation | One gateway for every model call: off unless the installation sets a provider and key by environment and the workspace switches each feature on; personal identifiers (email, phone, bank, card, national and tax IDs) removed before sending, pay, bank, tax and health fields never included; the assistant sees published help articles only and the reply draft never sees confidential cases; no database transaction held during a call; every call logged (redacted request, answer, sources, tokens, credits) in an insert-only table readable by auditors, text purged after the workspace's retention period; monthly credit cap per plan; AI output is a draft a person checks and sends or saves. Workflows: versions immutable, activation needs a passing test run, runs act as the activating person with permissions rechecked at every step and auto-pause if they lose access, idempotent per event, retries capped, confidential cases never trigger. Attrition scores visible only with `insights:attrition` (not managers), every view audited, rule-based with named factors | `modules/ai`, `modules/automation`, `modules/insights`, migration 0008 |
| Integrations | Owner-only (`integrations:manage`, two-step verification) and Business plan and up; API keys stored as SHA-256 hashes and shown once, read-only scopes only, act as their creator with grants cut to the scopes, refused on any route outside them, revoked keys frozen by trigger, last use recorded; webhook signing secrets and Slack URLs encrypted with the field key, shown once or masked; webhook bodies carry allow-listed ids only and are signed (HMAC-SHA256 with timestamp); outgoing calls refuse private, loopback, link-local and CGNAT addresses both when saved and at connect time, follow no redirects, time out after 10 s and keep 2 KB of the response; retries capped, failing endpoints switched off; every change audited | `modules/integrations`, migration 0009 |
| Single sign-on, provisioning and privacy requests | OpenID Connect (authorization code with PKCE S256, state and nonce single-use and expiring, ID token signature checked against the provider's published keys with exact issuer, audience, algorithm and a 10-minute age limit; verified email required and its domain must be one the workspace claimed, a domain can belong to one workspace only); a connection must pass a test sign-in before it can be switched on, and changing the provider or client puts it back to draft; enforcing it blocks password sign-in for everyone except owners (kept as break-glass) and signs out current sessions; just-in-time accounts respect the seat limit and get the Employee role only; the provider's `amr` counts as two-step verification only when it says `mfa`, `otp`, `hwk` or similar. SAML 2.0 (Phase 11): HTTP-Redirect AuthnRequest, HTTP-POST response to the Web Portal's `/sso/saml`, which passes it to the API; the assertion must be signed (RSA-SHA256) with the certificate the owner pasted (checked and fingerprinted on save, refused when expired), name CREW as audience and the ACS as recipient, be within its time limits (one minute of clock skew, ten-minute age limit) and answer the exact request CREW sent (InResponseTo, stored per sign-in and single-use); the IdP-asserted email is trusted only for the workspace's claimed domains (SAML has no `email_verified`); an authentication context of multi-factor kinds counts as two-step verification. Mobile single sign-on (Phase 11): the app sends only a PKCE challenge and an allow-listed return address (`MOBILE_SSO_REDIRECTS`); after the provider, the browser is sent to the app with a one-time code (stored hashed, two minutes, single use) that is exchanged for a session only with the matching verifier, and a mismatch is audited. SCIM 2.0 Users and Groups (Phase 11), behind a workspace token stored as a hash and shown once; deactivation suspends the membership and revokes sessions, owners cannot be deactivated, every request logged; groups grant a role only after an owner maps them, never the owner role, and leaving a group removes only roles that came from groups. Privacy requests (`privacy:manage`, two-step verification): access exports collect every record linked to the person with secrets removed, stored with a SHA-256 and every download audited; erasure only after the last working day and with no unfinalised payroll run, removes identity, contact, bank, tax and ID numbers, documents, helpdesk text and the sign-in account, and since Phase 11 also blanks free text written by or about the person (expenses, goals and check-ins, reviews and feedback, recognition, correction and overtime reasons, job-change and course notes, approval summaries, attrition scores, their own assistant conversations, notes, devices); frozen records accept exactly this change only inside the erasure transaction. It keeps payroll, attendance and the audit trail with the reason shown. A retention schedule (`privacy:manage`) can erase leavers a set number of years after their last working day, each through a privacy request, and deletes access exports and sign-in and provisioning logs after set periods; raw attendance punches are never deleted | `modules/identity`, `modules/privacy`, migration 0010 |
| Secrets | No secrets in code; configuration validated at start-up and the process refuses weak or missing keys | `platform/config` |

## Planned

- Phase 2: field-level envelope encryption (per-tenant data keys via KMS) for bank, tax and national ID fields; signed URLs for documents; malware scanning of uploads.
- Consent records and jurisdiction switches for location and biometric data (Phase 3 stores punch events only, never biometric templates).
- A Redis-backed session cache (rate limits are shared through Redis since Phase 11).
- After Phase 11: testing single sign-on and SCIM against real identity providers (Okta, Microsoft Entra ID), signed SAML requests and encrypted assertions, data residency cells, and an external penetration test by an independent firm. See `docs/compliance/controls-map.md` for how the implemented controls line up with SOC 2 and ISO 27001; CREW holds neither.
